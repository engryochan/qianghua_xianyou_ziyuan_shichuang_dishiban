## 二、確定的失敗機制

今天這一輪 `setuperr.log` 的因果鏈（時間序）：

```
11:26:51  MIG   Error loading hive C:\Windows\system32\config\elam.        → Win32 87
11:26:55  RegLoadKeyW failed to mount …\NewOS\WINDOWS\system32\config\SOFTWARE → 87
11:27:51  MIG   User profile loading error. Aborting due to external request.
11:27:51  SP    pSPDoMainGather: Engine initialization failed with error: 0x4
11:28:33  RegLoadKeyW failed to mount …\SafeOS\SafeOS.Mount\…\config\SYSTEM     → 87
11:28:33  SP    CEnableTelemetryForImage: Cannot load the system hive for the offline OS
11:28:35  SP    CAddCbsPackage::DoExecute: Failed to open new OS DISM session → 0x80070057
11:28:36  SP    ExecuteOperations: Failed execution phase Pre-Finalize
```

`87` 是 `ERROR_INVALID_PARAMETER`。失敗的不是某一個檔案，而是
**`RegLoadKeyW` 這條離線登錄檔掛載路徑整體**：NewOS 的 `SOFTWARE`、SafeOS 的
`SYSTEM`、以及目前系統自己的 `elam`，三者全部以同一個錯誤碼失敗。

### 本輪新增的關鍵證據：hive 檔案本身是好的

以一般使用者權限直接讀 `C:\Windows\System32\config\elam`：

| 項目 | 實測值 |
|---|---|
| 檔頭魔術字 | `72 65 67 66` = **`regf`**（合法登錄檔格式） |
| 大小 | 32,768 bytes |
| 最後寫入 | 2026-07-30 18:36:34 |
| 一般使用者可否讀取 | **可以** |

所以 `87` **不是檔案損壞、不是權限不足、不是檔案被鎖**。一個格式合法、
可被普通帳戶讀取的 hive，在 `RegLoadKeyW` 下被判為「參數錯誤」——這個形狀
指向**核心模式的登錄檔過濾驅動拒絕了該呼叫**。

（前一輪報告以 `RegLoadAppKey` 回傳 1009 作為旁證並自我提醒不可等同，
這點保留；本輪的 `regf` 檔頭與可讀性是新的、方向一致的獨立證據。）

兩個與本次失敗直接相關的細節：

1. **Kaspersky 註冊了開機啟動的 ELAM 驅動**
   `HKLM\SYSTEM\CurrentControlSet\Services\klelam` → `Start=0`、
   `Group=Early-Launch`、`system32\DRIVERS\klelam.sys`（18.0.147.0），
   備份在 `C:\Windows\ELAMBKUP\klelam.sys`。
   安裝程式失敗的第一個動作，正是載入 **`elam` 這個 hive**。

2. **亿赛通有一個名字就叫 `CDGRegedit` 的登錄檔元件在跑。**
   失敗的是登錄檔掛載呼叫。

另有一項時間吻合：`C:\Windows.old` 的時間戳是 **2026-07-30 17:35**，與
Kaspersky 的安裝日期（`InstallDate 20260730`）同一天——代表**在那之前就已經
有一次升級被回滾過**，本輪不是第一次。

## 六、給 IT 的請求（按優先序）

### 1. 先試這個——針對失敗點的官方支援開關（成本最低，請先做）

失敗的那個動作是
`Add package SSU-26100.9441-x64.cab to …\SafeOS\SafeOS.Mount`，
而這是 **Dynamic Update** 的步驟。關掉它，安裝程式就不必在 SafeOS 裡注入
SSU，也就不會走到那個掛載：

```powershell
F:\setup.exe /auto upgrade /DynamicUpdate disable /eula accept
```

這是微軟支援的 setup 參數，**不是**資安繞過。先前三次都沒用過這個開關。

**誠實的限制**：11:26:55 時 NewOS 的 `SOFTWARE` 掛載就已經失敗過一次
（只是當時沒中止），所以關掉 Dynamic Update **有機會但不保證**能過。
值得先試，因為成本極低。

### 2. 核對 Kaspersky 的目標 OS 相容性

請向原廠確認 **KES 14.1.0.423 是否支援 Windows 11 26H2（build 26300）**。
若不在清單上，請先用 Kaspersky Security Center 升級 KES 再重試升級——
它的 ELAM 驅動直接參與安裝程式的 hive 遷移。

### 3. 把安裝程式的工作目錄加進兩套 DLP 的白名單

亿赛通 Cobra DocGuard 與天锐绿盾，請白名單：

```
C:\$WINDOWS.~BT
C:\$WINDOWS.~WS
C:\$GetCurrent
C:\Windows\System32\config
```

### 4. 清掉殘留，再開新一輪（需管理員）

目前殘留：`C:\$WINDOWS.~BT`（11:52）、`C:\Windows.old`（07-30）、
`C:\$GetCurrent`。可用空間 87.8 GB。

```powershell
Dism /Online /Cleanup-Image /StartComponentCleanup
cleanmgr /sageset:65535
```

### 5. 若上述都失敗，帶著這些證據開微軟支援單

本目錄下已備好：`accept_*`、`lock-reconciliation.json`，以及
`../2026-10-05/Win11失敗證據_2044/`（`SetupDiagResults.xml`、`setuperr.log`、
`setupact-tail.txt`）。SetupDiag 的 profile 是
`FindAbruptDownlevelFailure`，`0x80070057 - 0x50015`。

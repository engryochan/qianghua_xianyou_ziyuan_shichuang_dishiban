## 一、最重要的發現：那份鎖版檔無法重建任何環境

第一次照 CLAUDE.md 的既定流程做

  cause: Because boto3==1.43.98 depends on botocore>=1.43.98,<1.44.0

我寫了一支可稽核的迭代鬆綁器（`診斷操作系統/Reconcile_PythonLock.py`，
每一次改動都寫進 `lock-reconciliation.json`）把矛盾全部挖出來。
**共六處內部矛盾，其中五處是真正不可化解的互斥：**

| # | 矛盾 | 性質 |
|---|---|---|
| 1 | `boto3==1.43.98` 要 `botocore>=1.43.98`，鎖版檔釘 `botocore==1.43.75` | 版本漂移 |

| 3 | `flair` 所有版本要 `transformers<5`；鎖版檔釘 `transformers==5.17.0` | **互斥** |
| 4 | `gevent==26.9.0` 在 win32 要 `cffi>=2.1.1`，鎖版檔釘 `cffi==2.0.0`（`ccxt` 也死釘 2.0.0） | **互斥** |

| 6 | `s3fs==2026.9.0` 要 `fsspec>=2026.9.0`，鎖版檔釘 `fsspec==2026.6.0` | **互斥** |

第 4 項值得單獨講：`gevent==26.9.0` 加 `cffi==2.0.0` 這**兩個釘選單獨放在一起
就已經無解**，跟我的任何鬆綁都無關。

### 根因的根因

**pip 安裝時不做全域求解。** 它逐一裝、遇到衝突只印警告然後照裝，
所以那個環境裡至少有五組套件一直跑在自己不支援的依賴版本上。
`pip freeze` 忠實地把這個**本身無解的狀態**拍成了快照。

> **推論：一份從未被真正用來重建過的鎖版檔，不是復原資產，只是一張照片。**
> 上一輪把它加進版控是對的（「復原用的鎖版檔本身也要進版控」），
> 但沒有補上最後一步——**拿它重建一次**。少了那一步，等於備份從未做還原測試。

### 兩個失敗的鬆綁策略（也都是教訓）

- **完全解除約束**會讓求解器為了閃避衝突一路回溯到史前版本：
  實測挖到 `sktime==0.8.0`（2021）與 `flair==0.2.1`（2018）。
  後者建置時直接死在
  `UnicodeDecodeError: 'gbk' codec can't decode byte 0x9d` ——
  **中文語系 Windows 下 `setup.py` 以 GBK 讀 README 爆掉**。
- **只用 `>=` 鬆綁**擋住了降版，所以遇到真互斥仍然無解。

最後採用的規則：**只在被迫時鬆綁；衝突時優先「收回鬆綁」而非丟套件；
仍無解才外移葉框架，共用底層（fsspec / toolz / cffi / plotly / transformers /
scikit-learn …）永不外移。** 42 輪後收斂。

### 驗收抓到了求解器核准、但實際壞掉的東西

第一次跑是 **14/15**，`lightgbm` FAIL：

```
TypeError: check_X_y() got an unexpected keyword argument 'force_all_finite'
```

`scikit-learn` 把 `force_all_finite` 改名為 `ensure_all_finite` 並移除舊名，
而鎖版檔釘的 `lightgbm==4.5.0` 還在呼叫舊名。依賴求解器完全看不到這件事——
**只有真的 fit 一次才會知道**。

修的過程又挖出第二層：升到 `lightgbm 4.6.0` 後 DLL 載入失敗
（`Could not find module ... lib_lightgbm.dll (or one of its dependencies)`），
但那個 DLL **明明在**（3.9 MB）。缺的是「它的依賴」：

| System32 | 狀態 |
|---|---|
| `vcruntime140.dll` | present 14.42.34438.0 |
| `vcruntime140_1.dll` | present |
| `msvcp140.dll` | present |
| `concrt140.dll` | present |
| **`vcomp140.dll`** | **MISSING** |

`vcomp140.dll` 是 **Microsoft OpenMP 執行期**。這台機器有 MSVC CRT 但沒有
OpenMP 執行期，而 lightgbm ≥4.6 連結它（4.5.0 不連結，所以 4.5.0 載得起來，
只是撞到上面那個 sklearn 參數）。登錄檔亦查無任何
Visual C++ Redistributable 安裝紀錄。

無需提權的解法：環境內 `sklearn\.libs\vcomp140.dll`（14.51.36247.0）已自帶一份，
就地複製到 `lightgbm\bin\`。之後實測
`lightgbm 4.6.0 | sklearn 1.9.1 | numpy 2.4.6 | acc=1.0000`。

#### 把這個權宜做法變成耐久的——而且我先否證了自己的第一個方案

複製到 `lightgbm\bin\` 的問題是**重裝 lightgbm 就會被覆蓋**。
我第一個想法是把 DLL 放到 `C:\work\runtime` 並加進使用者 PATH。
**實測否證**：把 `lightgbm\bin` 那份搬開後仍然失敗。

原因是 **Python 3.8 以後 Windows 的 DLL 搜尋改用
`LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`，不再搜尋 `PATH`**，
只找 DLL 自身目錄、`System32`、以及 `os.add_dll_directory()` 註冊的目錄。

正確做法是用 `.pth` 在解譯器啟動時註冊目錄。六個環境的 `site-packages`
各放一份 `zz_work_runtime_dlls.pth`：

```python
import os; os.path.isdir(r"C:\work\runtime") and os.add_dll_directory(r"C:\work\runtime")
```

`isdir()` 這個守衛不可省：`add_dll_directory` 對不存在的路徑會拋例外，
而 `.pth` 在**每次**解譯器啟動時執行，等於會弄壞整個環境。

驗證方式是把 `lightgbm\bin\vcomp140.dll` 搬開再跑：

```
RESOLVED VIA .pth add_dll_directory: lightgbm 4.6.0 acc=0.9900
```

（之後把本地那份放回去，兩層保險。）那條無用的 PATH 項目已撤回。

長期正解仍是請 IT 安裝 VC++ Redistributable——裝進 `System32` 就永遠找得到。

### 7. 「R 靠登錄機碼找 Rtools」這句不完整，照它做會失敗

CLAUDE.md 原本寫「R 靠登錄機碼 `HKLM\SOFTWARE\R-core\Rtools` 尋找」。實測：

- Rtools45 以 `/CURRENTUSER` 安裝後，機碼寫在 **`HKCU`**（`HKCU\SOFTWARE\R-core\Rtools\4.5.6768`），不是 HKLM；
- 但 `R CMD SHLIB` **仍然** 報 `'make' not found`。

R 4.5／4.6 的真正機制是 `etc\x64\Makeconf` 讀 **`RTOOLS45_HOME`** 去定位編譯器
（`LOCAL_SOFT = $(RTOOLS45_HOME)/x86_64-w64-mingw32.static.posix`），而
**`make.exe` 在 `rtools45\usr\bin`，必須在 PATH 上**建置才啟動得起來。

而我第一次測失敗還有第二層原因：安裝器把 `RTOOLS45_HOME` 設成**使用者層級**，
但我的 PowerShell 行程**早於它啟動**，所以看不到——
正是 CLAUDE.md 第 4 條教訓（`$env:` 是行程啟動時的快照）。

**解法：只在建置的工作階段設 `RTOOLS45_HOME` 與 `usr\bin`**，
或用 `Start_Analytics_v2.ps1 -WithToolchain`。

附帶再次驗證 CLAUDE.md 第 3 條：**gcc 在
`x86_64-w64-mingw32.static.posix\bin`，不在 `usr\bin`**——我在自己的入口腳本裡
把 gcc 寫成直接呼叫，於是 `-WithToolchain` 報
`The term 'gcc' is not recognized`。gcc 其實**不需要上 PATH**（Makeconf 會經
`RTOOLS45_HOME` 找到它），只有 `make` 需要。

## 二、**本輪最重要的技術發現（兩條，都推翻我自己的假設）**

### 2.1 `uv pip install --upgrade <名稱>` **不做全域求解**

我先前在報告裡寫過「uv 的求解器是全域的，衝突會在安裝前就報出來，
不會像 pip 那樣先裝壞再警告」。**這句話只對一半，而我用錯了那一半。**

| 指令 | 是否對全環境求解 |
|---|---|
| `uv pip install -r <完整需求檔>` | **是** |
| `uv pip sync <鎖版檔>` | **是** |
| **`uv pip install --upgrade <套件名>`** | **否**——只求解被指名者及其依賴 |

實測踩到兩次：

- 在 `xai` 升 `pandas` → 3.0.6，**違反 `dalex` 要 `pandas>=1.5.3,<3.0.0`**。
- 在 `rl` 升 `toolz` → 1.2.0，**違反 `gluonts` 要 `toolz~=0.10`**，
  同時 `pandas`、`deepdiff`、`virtualenv`、`mpmath` 也各自被違反，共 7 項。

**uv 全程沒有任何警告，離開碼 0。**

### 2.2 **`import X` 成功，不等於依賴宣告相容**

升壞之後我做的第一件事是試匯入：

```
toolz  1.2.0
gluonts  OK 0.17.0     <- 照樣匯入成功
tianshou OK 2.0.1
gevent   OK 26.9.0
```

**看起來毫無異狀。** 我一度因此以為「`toolz<1` 那條約束已經失效」。

但 `uv pip check` 說：

```
The package `gluonts` requires `toolz~=0.10`, but `1.2.0` is installed
```

而查 `gluonts` 的 metadata 證實該宣告確實還在：
`'toolz~=0.10'`、`'pandas<3,>=1.4'`。

> **教訓：匯入可用只證明模組載得進來，不證明它會正確運作。**
> `toolz` 1.x 改動過 API，`gluonts` 可能在特定路徑才出錯。
> **判斷環境一致性要用 `uv pip check`，不要用 `import`。**
> 本倉庫既有的「驗收標準是跑出結果」仍然成立，但這一條補在它前面：
> **連「跑出結果」之前，先確認依賴宣告沒被違反**——否則錯誤會延遲爆發。

### 2.3 正解：用約束檔把「不該動的」全部釘住

`ds` 第一次不帶約束升級，帶出 **28 項不相容**。原因是那 178 個升級
**連帶拉動了傳遞依賴**——`pandas`、`multidict`、`rich` 都不在我的指名清單裡，
是被順帶拉上去的。

> **自我更正**：我當時以為是工具誤判，查證後發現**工具其實正確地把 `pandas`
> 歸入 held**（計畫檔第 291 行，標 `-x 3.0.6`）。**錯在我的執行方式，不在工具。**
> 我把「指名清單」當成了「會變動的全集」。

正確做法是產生**約束檔**，把安全集合以外的**全部**釘在現版：

```
uv pip install --upgrade --constraint <約束檔> --python <解譯器> <安全集合...>
```

| `ds` 重做結果 | |
|---|---|
| 約束釘住 | 551 個 |
| 升級 | 178 個（302 行變動） |
| `pandas` / `cffi` / `multidict` | **全被守住未動** |
| `uv pip check` | **731 個套件，零不相容** |

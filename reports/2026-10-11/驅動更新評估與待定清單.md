## 一、「一律更新至最新版本」——照字面做會出事

**Windows Update 總共只提供一個驅動，而它是同代甚至更舊的版本。**

實測（唯讀 `Microsoft.Update.Session` 搜尋 `IsInstalled=0 and Type='Driver'`）：

```
WU 提供的驅動數 = 1
  - Realtek - Net - 4/9/2015 12:00:00 AM - 9.1.409.2015
    DriverClass : Networking
    DriverModel : Realtek PCIe GbE Family Controller
    HardwareIDs : pci\ven_10ec&dev_8168&rev_2b
    SizeMB      : 0.22
```

對照本機實際安裝：

| | 版本 | 日期 | 供應商 |
|---|---|---|---|
| **已安裝** | **9.1.412.2015** | 2015-03-31 | **Microsoft**（內建驅動） |
| WU 提供 | 9.1.409.2015 | 2015-04-09 | Realtek |

**版本號 412 > 409，但 WU 的日期較新。** Windows 的驅動排序先比日期再比版本，
所以 WU 才認為自己那份「較新」並提供它。**兩者都是 2015 年的驅動**，換過去毫無意義，
而版本號反而退了。

> **所以「一律更新」不能直接交給 Windows Update 執行。**
> 這台機器上 WU 能提供的唯一一個驅動，是個沒有價值的平移。

**而 WU 完全沒有那四個錯誤碼 28 設備的驅動。** 這點也實測確認了。

## 七、待定清單 #9：`vmcompute` 根因調查（已排除三項，已定位下一步）

`vmcompute`（Hyper-V 主机计算服务）每次開機逾時啟動失敗兩次
（10-11 06:52:07 逾時 45,000 ms、06:57:07 逾時 30,000 ms）。

### 已排除的三項

**一、不是「升級留下舊版執行檔」。這是我提出又自己推翻的假設。**

我先看到：

| 檔案 | `VersionInfo.FileVersion` |
|---|---|
| `C:\Windows\System32\vmcompute.exe` | **10.0.19041.4522** ← Windows 10 基底 |
| `vmcompute.dll` / `computecore.dll` | 10.0.26100.9549 |

看起來正是本倉庫記載的「系統版本跳了、元件沒跳」。但兩個數字讓我先驗證再下結論：
WinSxS 的 26100.9549 份與 System32 份的**最後寫入時間完全相同**，大小只差 33 bytes。
驗證結果**推翻了假設**：

| 比對項 | 結果 |
|---|---|
| 大小 | 兩者皆 **4,369,784 bytes** |
| SHA256 | 兩者皆 **`AEAFAC80551D223317AD4E55F47346AD53E8AFD571EEDE44CE7176FBF77D9388`** |
| `fsutil hardlink list` | **兩者互為硬連結，是同一個檔案** |

而關鍵在這裡：

```
FileVersion    : 10.0.19041.4522   ← 字串資源（OriginalFilename 指向 vmcompute.exe.mui）
FileVersionRaw : 10.0.26100.9549   ← 真正的二進位版本欄位
```

> **教訓：`VersionInfo.FileVersion` 是自由文字資源，可以與真實版本欄位不一致。**
> 它這裡來自 MUI 語言資源，所以寫著舊版號。判版本要用
> `FileMajorPart/FileMinorPart/FileBuildPart/FilePrivatePart`（即 `FileVersionRaw`），
> 更可靠的是雜湊與硬連結身分。
> **只看 `FileVersion` 字串就會得出「檔案是舊的」這個錯誤結論。**

**二、不是依賴失敗。** 四個依賴全部 Running：

| 依賴 | 狀態 |
|---|---|
| `rpcss` | Running / Automatic |
| `wcifs` | Running / Automatic |
| `condrv` | Running / Manual |
| `hvsocketcontrol` | Running / System |

**三、不是 hypervisor 沒載入。** `HypervisorPresent = True`，VBS 狀態為 2（已執行）。

> 附帶更正一個容易誤讀的欄位：`VirtualizationFirmwareEnabled = False`、
> `SecondLevelAddressTranslationExtensions = False` **不代表韌體虛擬化未啟用**。
> hypervisor 既已執行，它就接管了 VT-x，OS 回報的這些 CPU 欄位自然是 False。
> 既有報告已正確標註這一點。

### 功能影響：目前為零，但裝了發行版就會卡住

誰在開機時請求 `vmcompute`？`vmcompute` 本身是 Manual 啟動，所以有東西在叫它。
唯讀偵測結果：

| 元件 | 狀態 |
|---|---|
| `wsl.exe` | **存在** |
| `WSLService` | **Running / Automatic** |
| `HvHost` / `hns` | Running / Manual |
| `vmms.exe`、`virtmgmt.msc`、`WindowsSandbox.exe` | **不存在** |
| 排程工作 `\Microsoft\Windows\Containers\CmCleanup` | Ready |

所以裝的是 **WSL2／容器那一組**（不是完整 Hyper-V 角色），而 **WSL2 要靠 `vmcompute` 建立虛擬機**。

依規矩實測一次（`wsl.exe` 的輸出是 **UTF-16LE**，用單位元組編碼讀會變成字元間夾空白的亂碼，
必須以 `[System.Text.Encoding]::Unicode` 解碼）：

```
WSL 版本: 3.0.1.0   內核版本: 6.18.40.1-1   WSLg 版本: 1.0.79
MSRDC 1.2.7214   Direct3D 1.611.1-81528511   Windows 版本: 10.0.26300.9550
默认版本: 2
适用于 Linux 的 Windows 子系统没有已安装的分发。
```

**結論：WSL 3.0.1.0 已安裝、預設 WSL2，但沒有任何發行版。**
所以 `vmcompute` 失敗**目前沒有功能影響**——沒有東西要跑；
但**一旦裝了發行版就會卡住 WSL2**。

### #9 查明：不是壞掉，是半配置，而且沒有影響

### 新增 #13：升級失敗 hive 問題的最佳候選解釋

這是本輪最有價值的產出，因為 `fltmc` 正是三次升級失敗調查時**拿不到**的資料

| FLMonDrv | 370030 | 2 | Activity Monitor | minifilter |
| **Filelock** | **149998.99** | **0（Boot）** | **Encryption** | **傳統篩選器** |

**這是假設不是證明**，證實需停用該驅動後重新升級——違反資安規範，不做。
已出單子：`IT請求_篩選驅動堆疊與升級hive失敗_20261011.md`。

另記一條判讀紀律：**`LdMFilter` 的簽章者是 Microsoft WHCP，那只代表過了 WHQL

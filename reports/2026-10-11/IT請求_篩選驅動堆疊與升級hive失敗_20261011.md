## 三、最佳候選解釋：`Filelock` 是開機啟動的**傳統**加密篩選器

登錄檔載入設定（`HKLM\SYSTEM\CurrentControlSet\Services\<名稱>`）：

| 驅動 | Start | 群組 | 有 `Instances` 子機碼 | 模型 |
|---|---|---|---|---|
| **Filelock** | **0（Boot start）** | **FSFilter Encryption** | **否** | **傳統篩選器** |
| Estdlock | 1（System） | FSFilter Activity Monitor | 是 | minifilter |
| FLMonDrv | 2（Auto） | FSFilter Activity Monitor | 是 | minifilter |
| LdMFilter | 0（Boot） | FSFilter Activity Monitor | 是 | minifilter |
| KLIF.KES-14-1 | 1（System） | FSFilter Anti-Virus | 是 | minifilter |

`fltmc` 自己把 `Filelock` 標為 `<过时>`（英文版 `<Legacy>`），且該服務**沒有
`Instances` 子機碼**。兩項獨立證據一致：**它不是 minifilter，而是 FltMgr 之前
世代的傳統檔案系統篩選驅動**，以 `IoAttachDeviceToDeviceStack` 直接掛入裝置堆疊。

### 這條線索為何重要

三次升級失敗的機制已確定：

- `RegLoadKeyW` 對**所有**離線 hive 回傳 Win32 `87`（`ERROR_INVALID_PARAMETER`），
  涵蓋 NewOS 的 `SOFTWARE`、SafeOS 的 `SYSTEM`、以及本機的 `elam`。
- 失敗點固定在 **Pre-Finalize**，錯誤碼 `0x80070057 - 0x50015`。
- **換過兩種來源映像**（安裝助理 ESD 26200 / 官網 ISO 26300，SHA256 已核對），
  失敗簽名不變——所以不是映像問題。
- 相容性掃描乾淨：`ScanResult.xml` 全部 `BlockingType="None"`，
  `<Devices/>` 與 `<Programs/>` 皆空。
- **關鍵反證**：`elam` 本身是合法 `regf`、32,768 bytes、一般使用者即可讀取。
  **所以不是檔案損壞，也不是權限不足。**

Win32 87 正是「檔案開得起來，但內容不被登錄檔子系統接受」的典型回應。
而 `Filelock` 同時具備四個條件，剛好落在這條路徑上：

| 條件 | 為何相關 |
|---|---|
| **Start=0 開機啟動** | setup 掛載離線 hive 的每個階段它都在場 |
| **傳統（非 mini）篩選器** | 不走 FltMgr 契約，對現代檔案操作的相容性最差 |
| **FSFilter Encryption 群組** | 透明加解密會改寫讀回的內容，而 hive 必須逐位元組原樣讀取 |
| **2021 年的 Win7 DDK 二進位** | 比本 OS 組建早四年以上 |

### 界限：這是假設，不是證明

要證實只能做對照實驗——停用該驅動後重新升級一次。**我們不做，也不建議貴方
在未經原廠確認前這麼做**：該驅動屬公司資安管控，停用違反規範，且本機策略多半
已鎖定。使用者端全程唯讀，未啟停、未卸載、未重裝任何資安軟體。

Claude（第四輪：升上 Windows 11 之後的實測）

系統已就地升級到 Windows 11 Pro 25H2（26200.9457）。這一輪回答兩個問題：Comet 為什麼黑屏、其餘軟體是否還活著。

Comet 黑屏：根因不是顯示卡

先說我自己被推翻的推論。我一開始認定是 GT 730 配 2018 年驅動（實際版本 391.35，由 23.21.13.9135 末五碼反解）在 Windows 11 上算繪失敗。三個實測把它否決了：

  • --disable-gpu → 仍然 97.8% 全黑
  • 全新 --user-data-dir → 仍然 97.8% 全黑
  • 連分頁列與網址列都沒畫出來 → 黑在瀏覽器 UI 層，不是網頁層

然後用同一套像素判據做對照，答案就出來了：

瀏覽器 內容區近黑 平均亮度 相異色 結果
Chrome 0% 243.3 730 正常
Comet 97.8% — 160 黑屏

同一台機器、同一顆顯卡、同一個驅動。顯示路徑是好的。

真正的根因：DLP 只認得它名單上的瀏覽器

列舉行程載入的模組，差別立刻現形：

行程 被注入的 DLP 模組數
chrome.exe 18
msedge.exe 18
comet.exe 13

Comet 少掉的全是瀏覽器專用模組：BrowserGuardx64.dll、BrowerInject64.dll、LdBrowserMonitor64.dll、LdBrowserDataFlow64.dll、LdSendFileLimit64.dll、EstBrowserUrl64.dll、SQLiteDB64.dll。但通用掛鉤照樣注入，其中包含攔截繪製路徑的 LdWaterMarkHook64.dll（螢幕浮水印）。

天锐绿盾認得 chrome.exe / msedge.exe，不認得 comet.exe，於是只套了半套掛鉤——浮水印掛鉤進去了，讓它正常運作的配套模組沒進去，合成器輸出因此全黑。

這不是使用者能修的。正解是請 IT 在綠盾主控台把 comet.exe 加入受支援瀏覽器清單。不要把 comet.exe 改名成 chrome.exe 去騙過掛鉤——那是規避資安管控。

順帶抓到一套先前完全漏掉的管控代理

天锐绿盾（Tipray）裝在 C:\Inetpub\ftproot\Tipray\LdTerm\（行程 LdTerm.exe、LdApproval.exe），沒有標準的解除安裝登錄項。先前三輪診斷只比對「已安裝程式」清單，因此完全沒發現它。

教訓：偵測管控代理必須同時列舉行程實際載入的模組，只看已安裝程式會漏。

升級後的軟體存活狀況

唯一傷亡：%APPDATA%\uv\python 整個目錄消失，C:\work\envs\ds 的 site-packages 還在但底層直譯器沒了，venv 成為孤兒（Windows.old 裡也找不到）。

能救回來是因為當初產生了 requirements.lock.txt。但那個檔案只躺在 C:\work 裡、不在版控內——等於復原能力本身沒有備份。已收進 env/python-ds-requirements.lock.txt。

更正：上一節的根因結論不成立

上一節我寫「天锐绿盾只套了半套掛鉤，所以 Comet 合成器輸出全黑」。這個結論被我自己後續的實測推翻了，在此更正。

推翻它的反例

啟動 Positron（同為 Chromium／Electron 底）做第二個對照組：

應用 被注入的通用模組 渲染結果
Comet 13 個 近黑 97.9%、亮度 3.8 → 全黑
Positron 同樣 13 個（連 LdWaterMarkHook64.dll 都一樣） 近黑 1.3%、亮度 236.4 → 正常

模組集合完全相同，結果卻相反。「半套掛鉤 = 黑屏」不成立。

我錯在哪裡

我在「找到一個強相關」就停手了。模組數落差確實存在、也確實有意義（它證明 Comet 不在管控軟體的支援清單上），但相關不等於因果。正確的作法是繼續找反例——而一個 Positron 就足以推翻整個結論。

諷刺的是，這正是我在上一節用來推翻「顯卡驅動論」的同一種手法（拿 Chrome 當對照組）。我用對了方法否定別人的結論，卻沒有用同一把尺檢驗自己的。

目前確立的事實

已排除（皆為實測）：

假設 反證
GT 730 的 391.35 舊驅動 Chrome 近黑 0%、Positron 1.3%，同為 Chromium 底
設定檔損壞 全新 --user-data-dir 仍全黑
硬體加速 --disable-gpu 仍全黑
DLP 模組數較少 Positron 同樣 13 個模組卻正常
系統層級安裝損壞 更新程式遷移到使用者層級後重測，仍全黑

關鍵未解線索： Comet 連無頭截圖（--headless --disable-gpu --screenshot）都產不出檔案，而 Chrome 在完全相同的條件下正常產出 800×600、62 色的 PNG。這代表失敗不在螢幕合成層，而是整個瀏覽器在這個環境裡產不出任何輸出。

結論：目前沒有確立的正因。 誠實的說法只到「Comet 在這台機器上無法渲染，且不是上述任何一個原因」。需要 IT（管控軟體端）或 Perplexity（廠商端）進一步診斷。

順帶記錄的異動

測試期間 Comet 的更新程式（CometUpdaterTaskUser...，17:55 執行、result 0）把安裝從 C:\Program Files\Perplexity\（系統層級）遷移到 %LOCALAPPDATA%\Perplexity\（使用者層級），原目錄已清空。重測結果不變。

這一節的價值不在結論，在方法

三個結論在同一天之內被連續推翻——「舊顯卡 → 黑屏」被 Chrome 推翻，「半套掛鉤 → 黑屏」被 Positron 推翻。留下來的不是答案，是一份已排除清單和一個可複用的手法：

找同類但正常的應用當對照組，比對差異；找到差異後再找第二個對照組去否證它。

沒有第二個對照組，就只是換一個說得通的故事而已。
